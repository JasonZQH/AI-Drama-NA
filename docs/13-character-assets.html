角色资产与单镜头 Prompt

Status: Draft v1 · 2026-08-10 · 依赖：02-data-model.md、03-pipeline.md · 对应 ADR-0008

一致性不是写出来的，是管出来的。这一篇定义角色/场景资产的结构、生成顺序和质量闸门，以及单镜头 prompt 在流水线三个阶段各自该写什么。

1. 先理解模型怎么消费参考图#

设计资产结构之前必须接受三条机制事实，否则会做出看似合理、实际无效的设计。

1.1 视频模型没有人脸专用通路#

所有开源视频模型对参考图都是整图过 VAE、拼成 token。 Wan-Animate 中确有 Face Blocks，但它处理的是驱动视频的表情，且论文明确说明该通路被设计成「把表情信息与身份属性解耦」——身份 100% 来自参考图的整图 latent。

含义：不能指望模型「认出」哪张图是人脸参考并区别对待。把资产拆成脸/体型/服装三类，本身不产生收益；收益来自平台侧的 role routing，或 prompt 里的显式绑定。

1.2 平台的 role routing 能力差异巨大#

这张表直接决定资产要怎么绑：

平台 参考图上限 结构化 role 绑定方式 每角色多图
Gemini 3 Pro Image 6 物体 + 5 角色 + 3 风格 ✅ 类型化槽位，分开计数 类型化 ✅
Vidu Q 系列 7 🔶 subject 命名分组 @subjectname ✅ 每 subject ≤3
Kling VIDEO 3.0 — 🔶 Element 实体 元素绑定 ✅ 2–4/元素
Runway Gen-4 3 🔶 Reference 命名 @name ❌
Seedance 2.0 / 2.5 9 / 30 ❌ 无 @Image1 序号 ❌

在 Seedance 这类只有序号的 API 上，多视角参考有 identity splitting 风险（同一角色的多张图被判为不同身份），必须在 prompt 里显式声明「这几张是同一个人」，且需实测。

1.3 「高清大图」的收益在哪里饱和#

三条通路吃的东西完全不同：

通路 实际输入尺寸 高清是否有用
ArcFace ID embedding 112×112（5 点对齐裁剪） ❌ 早已饱和
CLIP face crop（IPA-Plus） 224×224 🔶 224 处饱和
整图 VAE（视频模型） 原生分辨率 ✅ 真正吃分辨率
inswapper 换脸 固定 128×128 进出 ❌ 必须配超分

但存在明确下限：人脸瞳距低于约 48px 时识别性能显著退化。

执行结论：不要为「把一张脸做到 4K」投入预算。把同样的成本转投到做齐 3–5 个角度，ROI 高一个数量级。硬指标是瞳距 ≥48px（下限）、≥100px（安全线，约对应 300–400px 见方的人脸区域），单图 ≥1024×1024。

1.4 远景人脸崩坏是数学必然#

Wan2.2-VAE 空间压缩 16×16，叠加 DiT 的 2×2 patch，1 个 token = 32×32 像素。720p 全身镜头里人脸约占画面高度 1/8 ≈ 90px，即整张脸只有约 2.8×2.8 个 token。

不到 9 个 token 要承载全部身份信息——崩坏不是模型能力问题，是没有 token 预算。而且 Wan2.2 的压缩率比 Wan2.1（16×16 像素/token）更激进，这个问题更严重。

这条直接变成分镜层的硬规则，见 §5.1。

2. 角色资产结构#

Character
├─ profile            结构化文本（角色卡）
├─ face_set           人脸基准组 ★
├─ body_ref           体型基准 ★
├─ wardrobe[]         服装套装 ★
├─ expressions        表情表
├─ lora?              可选私有权重
└─ platform_bindings  各平台的 role 绑定

2.1 face_set — 一组，不是一张#

ts
face_set: {
  primary:       AssetId    // 正面 · 中性表情 · 均匀光照 · 白底
  profile_left:  AssetId    // 左侧面
  profile_right: AssetId    // 右侧面
  three_quarter: AssetId[]  // 3/4 侧，覆盖最常用的镜头角度
}

推荐配置是正面 + 两个侧面起步，即经典三视图。只给正面时，模型会把正面特征错误投影到侧视图上，产生不自然几何或 mean face effect。

入库校验（自动执行，不过闸不许入库）： - 人脸可被检测器检出（检不到 = 整条 face 通路失效） - 瞳距 ≥100px，图像 ≥1024×1024 - 中性表情、均匀光照、纯白背景 —— 参考图要当「空白画布」用，任何姿态/光照/背景都会被 copy-paste 搬进输出

2.2 body_ref — 是否含头取决于画风#

ts
body_ref: {
  full_body:    AssetId          // 正面 + 背面全身
  head_policy:  'keep' | 'strip' // 由画风决定，见下
  pose_map:     AssetId?         // head_policy='strip' 且为风格化比例时必填
}

去掉头部后损失的只是「头身比」这一个绝对尺度锚点，不是全部体型信息——肩宽、四肢长度、躯干比例在颈部以下依然完整保留。所以代价大小完全取决于画风：

画风 head_policy 理由
写实比例（真人感短剧、多数都市/现代题材） strip 去头 模型先验能自动补上正常头身比，去头几乎零代价，且能彻底消除身份污染
风格化比例（Q 版、刻意的 8 头身 / 6 头身设定） keep 留头，或 strip + 必填 pose_map 头身比本身就是核心人设，去掉必然飘

默认取 strip——短剧绝大多数是写实比例，且去头带来的身份污染消除是确定收益。

实践验证与机制解释【来自 Hell Grind 开源管线，95 分钟 AI 长片】：其角色资产包就是三张图——面部特写、去掉头部的正面全身、背面全身。

去头的真正原因比「避免污染」更具体：生成远景/全景镜头时，模型会去读全身参考图里那张又小又糊的脸，反而把脸画坏。去掉头部等于强制信息通道隔离——身体信息只从全身图取，脸只从特写图取。

这解释了为什么去头有效，也解释了它的边界：它解决的是「劣质脸信息干扰」，不是「脸信息本身有害」。所以 §2.1 的人脸特写必须同时存在，两者是配套的，缺一不可。

学理侧的对应佐证：Parts2Whole 能抠掉脸仍保持体型，是因为它额外输入了一张 pose map；VTON 能用平铺服装图，是因为 person image 提供了完整体型与姿态。两者都补了几何信息——这正是风格化比例下必须补 pose_map 的原因。

若因其他原因需要保留头部但又怕污染，用降级而非删除：轻度模糊保留头部轮廓。

2.3 wardrobe — 穿着态 + 抠到服装区域#

四种做法的取舍：

方案 保版型垂坠 消除身份污染 保尺度锚点 评价
平铺无人（VTON 标准） ❌ ✅ ❌ 只答「这件衣服长什么样」
完整穿着带脸 ✅ ❌ ✅ identity splitting 风险最高
穿着态 + parsing mask 抠服装区 ✅ ✅ 🔶 推荐
穿着态裁到下颌线以下 ✅ ✅ 🔶 工程上最简单的近似
ts
wardrobe: [{
  id, name,
  worn_masked: AssetId    // 推荐：human parsing 抠出服装区域
  flat_lay:    AssetId?   // 备选：平铺
}]

注意 VTON 领域的真实做法：它从不「去掉脸」，而是把脸放在另一张图里、并用 inpainting mask 保护起来不让模型重绘。精神与你的直觉一致，但实现更强——不是「不提供脸」，是「提供脸并锁定它」。

2.4 角色卡（结构化文本）#

ts
profile: {
  name, age, gender,
  appearance:   { hair_style, hair_color, facial_features },
  anchor_tokens: string[],    // 2–3 个唯一性强的锚定词，如「红围巾」「蓝校服」
  prohibited_changes: string[], // ★ 禁止变化项：任何镜头都不许漂的特征
  personality_tags: string[],
  voice_id: string,
}

anchor_tokens 用于图生图阶段的冗余校验（§4.2）；prohibited_changes 用于人审 checklist 与自动评测的比对基准。

2.5 场景与道具资产#

场景硬规则：全景、无人物、环境完整。 带人的场景图做参考时，模型会把图里的人一起带进来，与角色资产冲突。

时间/光线是变体维度，每个变体是一张独立入库的图，不靠 prompt 临时改光。

命名规范（三类资产共用二段式）：

角色：{name}_{阶段或套装}     林野_17岁、林野_校服
场景：{name}_{时间光线}       舅舅家客厅_白天
道具：{name}_{状态}           酒杯_完整、酒杯_破碎

3. 资产生产顺序（S4 阶段的展开）#

① 从剧本抽角色卡（LLM）
② 文生图定妆 → 抽卡（单角色 4–16 张起）
③ 选定主图 → 局部精修（眼睛/手/服装细节）
④ 以主图为参考，图生图产出 face_set 各视角 + 表情表 + 体型图
⑤ 入库：命名 + 白底 + 质量闸门校验 + 色卡标注
⑥ 锁定（locked 后才允许进入 S5 批量生成）

S4 未完成时，分镜页的批量生成入口必须禁用。 参考图没锁死就开始批量生成，等于在流沙上盖楼——「角色设定未完成就开工」是行业公认的五大失败模式之一，后果是一致性问题级联放大、中途修正代价极高。

4. 单镜头 Prompt：三阶段差异化#

Prompt 的槽位模型是稳定的五槽，但三个阶段填的槽完全不同。

style | shot(景别+机位+运镜) | scene | subject + action + expression | lighting

4.0 两层结构：固定底座 + 可变正文#

Hell Grind 对 4 万余条 prompt 的公开数据显示一个清晰的两层结构，值得直接采用：

A. 技术底座（全片恒定，逐条 prompt 完整重复）
   风格 / 摄影 / 机身镜头 / 光照 / 色彩 / 肤质 /
   物理规则 / 表演基调 / 构图 / 连续性 / 技术参数 / 音频
   —— 约 12 行，做成配置文件，由模板引擎自动拼接

B. 镜头正文（逐镜变化）
   ① 角色状态（外貌 / 伤情 / 服装破损 / 表情）
   ② 承接上一镜（显式写清前一镜结束时的状态）
   ③ 导演意图（这一镜要传达什么）
   ④ 位置几何（谁站哪、距离几米、朝向）
   ⑤ 对白 + 音效
   ⑥ 动作序列（按秒排时间码）
   ⑦ 硬约束（从失败中积累的清单）

底座层是纯配置，不该由人逐条写——他们的数据里某一行技术参数重复了 8000 多次。这正是 prompt-kit 模板引擎该干的事（01-architecture.md §4 第 ④ 步）。

本项目的目标长度：底座 12 行 + 正文 500–800 字。 更短的 prompt 引入的互相冲突指令更少，在批量场景下反而更稳。

4.1 文生图阶段（出定妆图 / 首帧）#

全槽位填充 + 参考图。双保险，因为此时还没有可依赖的资产。

4.2 图生图阶段（出分镜静帧）#

参考图承载外貌，prompt 只写差异项 —— 本镜特有的表情、动作、景别、光线，外加 2–3 个 anchor_tokens 做冗余校验。

不要重复完整外貌描述。参考图已经承载了它，重复描述反而增加与参考图冲突的机会。

4.3 图生视频阶段#

只写「运动 + 运镜」。 这是阿里云百炼官方对图生视频 prompt 的明确口径——主体、场景、风格已由图承载。

prompt = action + camera_move

在这个阶段重复角色外貌描述是常见错误，它会与首帧图争夺控制权。

4.4 镜头语言词汇表#

统一采用中英双语写法，存为枚举而非自由文本：

景别 特写 Close-up · 近景 Near shot · 中景 Medium shot · 全景 Wide shot · 极端全景 Extreme wide shot 运镜 推进 Push in · 拉远 Pull back · 左移 Pan left · 右移 Pan right · 上摇 Tilt up · 下摇 Tilt down · 环绕 Orbital · 固定 Fixed shot 机位 平拍 Eye level · 俯视 Bird's eye · 仰视 Low angle · 过肩 Over-the-shoulder · 航拍 Aerial 光线 日光 Daylight · 柔光 Soft light · 硬光 Hard light · 侧光 Side light · 边缘光 Rim light · 背光 Backlighting · 顶光 Top light

每镜只写一个运镜。

4.5 Prompt Lint 规则（做成校验，不是自由文本）#

这些必须在分镜阶段就拦截，而不是等生成完才发现：

规则 说明
禁抽象心理描写 「心里很痛苦」→「双拳紧握、低头颤抖」
禁抽象动作 「眼神流转」「指尖划过」这类模型无法解析
禁复杂光感术语 「电影级光影」「丁达尔效应」
禁 3 人以上复杂互动 「三人同时打斗」必然崩
机位物理可能性 如「低角度俯拍平放在桌上的手机屏幕」是矛盾描述
单镜时长 3–8 秒
单句台词 ≤10 字 同时校验 TTS 时长是否超镜头时长
Prompt 长度软告警 单镜 >200 字提示。长 prompt 尾部指令遵循度会下降

最贵的一条教训：不要用否定指令。 Hell Grind 团队公开把这条列为代价最高的失误——写「No held object」，模型偏偏塞给角色一把武器。扩散模型主要识别正面内容，否定词经常反向生效。必须改写成正面描述：不写「手上没有东西」，写「双手空着、手掌张开、垂在体侧」。

Lint 规则里应当加一条：检测到 不要 / 没有 / 无 / no / without / avoid 等否定式描述时告警，提示改写为正面描述。

注意：国产闭源视频模型的负向提示词能力普遍弱于 SD 体系，阿里云官方指南完全没提负向词。把禁写规则做成 lint，比依赖 negative_prompt 字段有效得多。

数字化而非形容词化。 同一来源的另一条核心写法：模型吃数字不吃形容词。运镜写「从 8 米推到 4 米，机位高度 3 米降到 2 米」而不是「缓缓推近」；速度写「比常规推轨快 3 倍」而不是「快一点」；镜头写具体焦段（24mm 低角度 / 50mm 环绕 / 85mm 特写）。这条可以做成 prompt 模板的字段约束——把机位、距离、焦段做成结构化数值字段，而不是自由文本。

4.6 动作幅度约束#

大动作是失败高发区——会造成肢体扭曲、面部退化、服装混乱。有效的做法是把动作控制在：细微的头发/布料摆动、缓慢推镜、轻微口型、背景氛围与光线变化。

「控图不控视频」：视频质量取决于底图质量。把精力放在静帧上，视频阶段只做小幅度运动。

5. 一致性的工程规则#

5.1 景别与身份的硬约束（来自 §1.4 的 token 预算）#

镜头用途 景别要求 人脸在输出帧的高度
身份建立、情绪表达 中景以上 ≥150–200px（Wan2.2 下 ≥5×5 token）
叙事推进 中景 ≥120px
环境交代、转场 全景可用 不承担身份识别

全景镜头不要指望人脸正确。需要全景又需要认脸时，两个办法：提高输出分辨率（720p→1080p 让人脸 token 数增加 2.25 倍），或走 FaceDetailer 式两段式修复（检测人脸 → 在全图分辨率下 inpaint 重绘该区域 → 缩回贴合）。

5.2 绝不递归#

每个镜头都从固定的原始角色资产重新起算，绝不用上一个镜头的输出帧当下一个镜头的参考图。

递归漂移是指数放大而非线性的：训练时模型看到的条件帧是干净的，推理时是自己生成的带误差帧，这个分布错配让误差进入模型没见过的输入域，输出误差更大，形成正反馈。业界的通俗表述是「a copy of a copy」——十秒片段结束时，微小误差已经放大成完全不同的角色。

shots.continuity_from_shot_id（02-data-model.md）的正确用法是取前序镜头选定 take 的末帧作为本镜 i2v 的首帧条件，同时角色参考图仍然来自 master 资产。两者是叠加关系，不是替代关系。

高危时刻：角色转身、被遮挡、走出画面再回来。这些时刻最近的上下文里没有脸可参考，是 identity drift 的高发点，应在分镜阶段就规避，或在遮挡后强制重新注入参考。

「尽量只过一次生成」要正确翻译。 这是电影级制作者常给的建议——每多过一道生成就多叠一层误差，所以能一次到位就别返工。但电影和批量短剧的可行解不同：一部 95 分钟电影的主角团人数有限、单镜可以精修，靠「一次生成 + 人工挑选」能保证质量；一部 60 集短剧有 3000+ 镜头，人工兜不住。

在本项目的量级下，这条建议应翻译成 「提高一次通过率」，而不是「不重试」——即把预算投在参考资产质量、prompt lint、景别约束上，让首次尝试就过闸的比例上升（这正是 12-roadmap.md 把一次通过率列为核心指标的原因），而不是取消 03-pipeline.md §3 的重试升级策略。两者不矛盾：减少重试次数是目标，保留重试能力是手段。

5.3 seed 不是一致性机制#

把 seed 定位成可复现性字段，不是一致性功能。 大量中文教程在这点上是错的。

seed 只在其余参数完全不变时保证可复现。prompt 一改（换景别、换动作），同 seed 出来的人脸就会变。真正产生一致性的是参考资产、平台角色 ID、或 LoRA。seed 的价值在于防止参数漂移的纪律与事后可复现，不在于产生一致性。

5.4 LoRA 训练集：与社区默认建议相反的一条#

社区指南通常建议「不要混入不一致的服装」——那是为「角色总穿同一套戏服」的用例写的。

短剧场景必须反过来做：服装、背景、光照都要多样化。 否则 LoRA 会把戏服学进身份，导致换装时身份漂移。原理与学术侧一致——要让某个属性不被学进身份，就必须在数据里让它随机变化。

关于「特写 : 半身 : 全身」的最优配比，没有找到任何权威来源。网上流传的具体数字缺乏可追溯依据，建议用自己的素材做小规模 A/B，成本低且能直接决定 schema。

5.5 角色间辨识度#

行业普遍现象是所有角色收敛到同一张「梦幻脸」，观众要靠发色区分。这是被普遍忽略但真实存在的痛点。

建议在资产层加一条闸门：新角色入库时，与项目内已有角色做身份 embedding 相似度比对，过高则告警。这是「角色自身一致性」之外的另一个维度。

5.6 群像与大场面：用物理遮蔽掩护模型的失败区#

批量生产里最容易崩的是人群、街景、战斗大场面。Hell Grind 的做法是三层堆叠 + 雾：

层 处理
前景 少数几个角色清晰可辨，有完整描述
中景 人群只提供密度，不给个体细节
背景 只剩剪影
全局 加厚雾把能见度压到约 20 米内

关键在最后一条：用叙事上合理的物理遮蔽（雾 / 烟 / 雨 / 夜 / 浅景深）为模型必然崩坏的区域提供掩护。这不是偷懒，是把「模型能力边界」翻译成「美术设定」。

对短剧的迁移价值很高，而且模型越弱收益越大——你用自部署开源模型时比用闭源旗舰更需要这一条。分镜阶段就该把大场面写成「有遮蔽理由的大场面」。

5.7 废片碎片抢救#

在低采纳率下，被否决的生成里必然埋着大量可用的 1–3 秒片段。Hell Grind 的做法是把这些碎片提取入库，当作连接镜、插入镜复用。

工程含义：takes 表的 rejected 状态不该等于「无价值」。建议加一条轻量流程——人审拒绝一条 take 时，可标记「部分可用」并框选可用时间段，产出一条 kind=fragment 的派生 asset，按角色/场景/情绪打标进碎片库。

这条在 98% 都是废片的现实下，是唯一能把沉没成本变回资产的机制。

5.8 采纳率标定：M1 的第一个实验#

采纳率（首次生成即被采用的比例）直接决定算力预算能否成立：

采纳率 3000 镜的剧需要的生成次数
10% ~3 万次
25% ~1.2 万次
40% ~7500 次

M1 阶段必须先测出自己质量标准下的真实采纳率，这个数字比任何模型选型都更能决定项目可行性。

提高采纳率的杠杆按 ROI 排序：① 参考资产质量（§2）② prompt lint 拦掉必崩的镜头（§4.5）③ 景别约束（§5.1）④ 物理遮蔽（§5.6）。这四条都在生成之前，比事后重试便宜一个数量级。

5.9 失败模式 QC 清单#

来自 Hell Grind 管线的社区整理，八类，可直接做成审片 checklist 与自动检测项：

失败模式 症状 处理
帧率漂移 有重复帧，实际帧率掉到 12–18fps prompt 里显式声明帧率；剪辑去重帧。可自动检测（T0 层）
单帧缺陷 一帧手/脸崩掉毁掉整条 逐帧 scrub；每 10 秒片段预算 30–60 秒审查
关键帧幻觉 首帧里没有的元素被模型凭空放进来 显式写「该元素在首帧中不可见，它在…时出现」
物理状态漂移 只该动 A，相邻的 B 也跟着动 显式命名不变量：「X 固定在表面，只有 Y 移动」
多运镜过载 叠加运镜产出无法阅读的画面 一镜一个主导运镜；复合运镜必须写成带时间码的序列
空间感失败 进门、走廊、家具穿模 加空间布局块：机位、地面参照、行进方向
内容分类器误判 干净 prompt 被拒 泛化解剖学词汇，替换感官形容词
废片可抢救 整条被否但有 1–3 秒可用 见 §5.7

前两类和第五类可以做成自动检测进 T0/T1 层（03-pipeline.md §4），其余是人审 checklist。

6. 数据模型影响#

对 02-data-model.md 的 characters 表的具体修改见该文档 §3.3。要点：

  • reference_asset_ids 单一数组不够，需拆成 face_set / body_ref / wardrobe 三个结构化字段
  • 新增 anchor_tokens、prohibited_changes
  • 新增 platform_bindings（各平台 role 绑定不同，且有数量上限）
  • 资产入库需要质量闸门字段：face_detected、inter_pupillary_px、resolution

7. 待验证清单#

以下几条机制推理明确但缺少直接消融实验，建议用自有素材做小规模 A/B（成本低，且直接决定 schema）：

  1. 风格化比例角色在 head_policy='strip' 下的实际漂移幅度 —— 写实比例已有实践验证可去头，风格化侧无直接实验
  2. 单图 grid 三视图 vs 三张独立图 —— 无直接对比。机制上倾向分开（分辨率预算 9 倍差、位置编码天然按图分离），但未实测
  3. LoRA 训练集的景别配比 —— 无权威来源
  4. 在 Seedance 这类无 role routing 的 API 上，多视角参考的 identity splitting 实际发生率
