# ADR-0009 · 部署拓扑：模块化单体 + 无状态计算 worker，不上微服务

- **状态**：已接受
- **日期**：2026-08-11
- **相关**：`01-architecture.md`、ADR-0001、ADR-0003、ADR-0005

## 背景

系统跑五个进程：Web、控制面、控制面的队列消费者、Python 视频 worker（远程 GPU）、Python 媒体 worker。这个形态容易被误认为微服务，需要一次明确定性，否则后续会不断有人提议「把 X 拆成服务」。

先澄清一个常见的维度混淆：**monorepo / polyrepo 决定源码放在哪，monolith / microservices 决定运行时怎么拆，两者正交。** Google 与 Uber 都是 monorepo + 大规模微服务。ADR-0001 回答的是前者，本 ADR 回答后者。

## 决策

**当前架构定性为「模块化单体 + 无状态计算 worker」，明确不是微服务，且短期内不向微服务演进。**

- 控制面是一个可独立部署的模块化单体（`domain` / `pipeline` / `providers` / `queue` / `routes`）
- Python worker 是无状态计算单元，不拥有数据、不含业务上下文
- Postgres 单写者：只有控制面进程有写权限（ADR-0003）

## 理由

**Python worker 不是微服务，是远程函数。** 它们被拆成独立进程只有一个原因——需要 GPU 与 Python 运行时，而开发机没有。这是**硬件与运行时边界，不是有界上下文边界**。worker 不知道 Project / Episode / Shot 是什么，不连数据库，收 prompt 与图 URL、吐 storage key。

这个区分决定了不该给它们上服务网格、服务发现、分布式追踪——它们只需要一个 HTTP 端点和健康检查。

**单写者 Postgres 是本系统的命门，而它与微服务互斥。** 微服务的定义性特征是 database-per-service。但本系统的核心资产是 Generation Ledger——要能用一条 SQL 回答「某 provider 在某镜头类型上的每可用镜头成本」，这需要 job / shot / take / asset / eval 在同一个库里 join（`02-data-model.md` §4）。拆库之后这个查询就没了，得靠事件溯源或数据仓库把它重新拼回来，**为了换回现在免费就有的能力**。

事务层面更危险：现在「创建 generation_job + take + asset」是一个 Postgres 事务。拆成服务后变成 saga，需要补偿事务——而在这个领域里，**补偿失败意味着 GPU 时间已经烧掉、产物却对不上账**。

**微服务的主要收益是组织性的。** 它让多个团队独立发版。当前是单人开发，成本（分布式事务、最终一致性、网络故障模式、跨服务调试）全付，收益为零。

**当前位置本身是舒服的**：GPU worker 已经跑在异构硬件上、跨网络、独立镜像、独立扩缩——**已经拿到分布式该给的好处（异构硬件、独立扩缩），而没有付分布式数据的代价。**

## 代价与缓解

**代价**：控制面是单点，重启会中断 API（队列任务由 reconcile 恢复，`05-job-orchestration.md` §8）；所有后端逻辑共享一个发版节奏。

**缓解**：模块边界靠构建期强制而非运行时协议（`01-architecture.md` §5）。守住「模块之间只通过带显式类型的函数调用通信、不共享可变状态」这一条，将来抽服务就是把函数调用换成 HTTP 调用，不需要重构领域逻辑。

## 重新评估的触发条件

出现任意两条即值得评估拆分：

1. **播放侧与生产侧并发需求差出一个数量级** —— Studio API 是几十 QPS，播放控制面可能是几千。届时把 playback control plane 拆出去是合理的（读多写少、可用只读副本）
2. **有 2 名以上后端开发，且发版经常互相阻塞**
3. **eval 服务需要自己的模型常驻**（M6 的 VLM 评测），其资源画像与扩缩节奏与控制面完全不同

**注意这三条都不是「代码变多了」。** 代码量增长的正确解法是拆模块，不是拆服务。
