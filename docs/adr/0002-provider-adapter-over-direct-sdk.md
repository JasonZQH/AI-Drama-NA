# ADR-0002 · 用 Provider 适配器而非直连厂商 SDK

- **状态**：已接受
- **日期**：2026-08-10
- **相关**：`04-provider-adapter.md`

## 背景

视频生成后端有多个候选：云 API（Vidu、Kling、即梦/Seedance）与自部署开源模型（Wan2.2、HunyuanVideo）。它们的接口、参数、错误码、计费方式完全不同。

行业变动极快：模型每季度更新、价格频繁调整、有的模型从开源转闭源、有的 API 突然改内容政策。

## 决策

**定义统一的 `VideoProvider` 接口，所有生成能力藏在它后面。业务代码永远不 import 任何厂商 SDK。**

统一的 `GenerationRequest` / `GenerationResult` 是 provider 中立的；每家的差异由各自适配器翻译；私有参数走 `providerParams` 逃生舱，且只有对应适配器可读。

## 理由

**换后端的成本必须是改一行配置。** 如果业务代码里散落 `import { ViduClient }`，一次 provider 变动要改几十处，而这种变动一年会发生好几次。

更重要的是：只有统一接口才能做**同口径对比**。「Vidu 在特写镜头上的每可用镜头成本 vs 自部署 Wan2.2」这个问题，前提是两条路径产生结构相同的记账数据。没有适配器层，这个对比根本无法进行，而它恰恰是整个技术选型的核心问题。

`MockProvider` 作为一等公民实现，是「无 GPU 无 key 也能跑通全链路」这条硬约束的载体。

## 备选与否决理由

| 方案 | 否决原因 |
|---|---|
| 直连单一 provider | 锁定风险高；无法比较；政策变动即停摆 |
| 用第三方聚合服务 | 多一层抽成与故障点，且聚合层自己也会改接口 |
| 每个 provider 一套独立业务流程 | 重复代码，记账口径不一致，无法比较 |

## 后果

**正面**：可替换、可比较、可 mock；新增 provider 只需实现接口 + 通过契约测试。
**负面**：抽象有成本——某些 provider 的独有能力（如原生音画同步）要么放进 `capabilities` 让路由器感知，要么牺牲。
**缓解**：`capabilities` 声明式描述能力差异，路由器据此过滤；`providerParams` 提供逃生舱，避免为个别参数污染通用模型。
