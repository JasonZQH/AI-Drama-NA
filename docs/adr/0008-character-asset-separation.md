# ADR-0008 · 角色资产按 face / body / wardrobe 三路分离

- **状态**：已接受
- **日期**：2026-08-10
- **相关**：`13-character-assets.md`、`02-data-model.md` §3.3、`03-pipeline.md` §S4

## 背景

v1 的 `characters` 表用单一 `reference_asset_ids` 数组承载全部参考图。实践中提出的疑问是：人脸是否应该有一张单独的高清基准图，而服饰图与体型图是否应该去掉人脸，以免人脸在视频生成中被带偏。

## 决策

**角色参考资产拆成三路结构化字段：`face_set`（多视角人脸基准）、`body_ref`（体型基准，去头策略随画风）、`wardrobe`（服装套装，抠掉脸）。**

## 理由

三类资产的构图要求、质量闸门与失败模式完全不同，放在同一个数组里既无法校验也无法按平台的 role 槽位分发：

| | 构图要求 | 质量闸门 | 主要失败模式 |
|---|---|---|---|
| face_set | 多视角、中性表情、均匀光照、白底 | 人脸可检出、瞳距 ≥100px | 单视角导致侧脸 mean face effect |
| body_ref | 正面 + 背面全身；去头与否按画风 | 完整站姿 | 风格化比例下去头会丢失头身比锚点 |
| wardrobe | 穿着态 + parsing mask 抠服装区 | 无可识别人脸 | 带脸导致 identity splitting |

## 三条被证伪或修正的直觉

**① 「一张」高清人脸基准图 → 应为一组多视角。** 单视角参考不足以在不同面部角度下保持身份，会把正面特征错误投影到侧视图。HarmoView 多视角 74.70 vs 单视角 72.61；Mv2ID 多视角 MvRC-Arc 0.544 vs 单视角 0.408–0.493。推荐配置为正面 + 两个侧面。

**② 「高清」的收益极早饱和。** ArcFace 识别输入固定为 112×112 对齐裁剪，inswapper 固定 128×128 进出。人脸区域超过约 512px 后对 ID embedding 几乎零增益。真正吃分辨率的是视频模型的整图 VAE 通路。硬指标应写成瞳距下限（48px）与安全线（100px），而非「越高清越好」。**预算应从「把一张脸做到 4K」转投到「做齐 3–5 个角度」。**

**③ 体型图是否去脸，取决于画风，不能一刀切。**（本条为 2026-08-10 修订，初版曾武断地写成「必须含头」）

去头损失的**只是头身比这一个绝对尺度锚点**，肩宽、四肢长度、躯干比例在颈部以下完整保留。因此：

- **写实比例**（短剧的绝大多数）→ 去头，模型先验能补上正常头身比，且彻底消除身份污染。**取为默认值。**
- **风格化比例**（Q 版、刻意的头身比设定）→ 留头，或去头但必须补一张 pose map。

学理佐证仍然成立，只是适用范围收窄：Parts2Whole 能抠掉脸仍保持体型是因为额外输入了 pose map，VTON 能用平铺服装图是因为 person image 提供了完整体型与姿态——**这解释的是「风格化比例下为什么必须补几何信息」，而不是「所有情况都必须含头」。**

**实践验证**【非论文】：一位完成过 95 分钟 AI 电影的制作者公开分享的角色卡结构为「去掉头部的正面 + 背面全身图 + 单独的人脸特写」，与本 ADR 的 face_set + body_ref(strip) 组合一致，可作为写实题材的默认形态。

## 服饰图去脸成立，但机制与直觉不同

去脸这一条成立——Runway 官方明确建议用黑框盖住参考图中的无关人脸。但真实机制不是「多张脸被平均糊掉」，而是两条：

- **identity splitting**：同一角色的多张图若存在妆造/光照/画风差异，会被判为不同身份
- **copy-paste shortcut**：参考图的姿态、光照、轮廓被整体搬进输出

注意 VTON 领域的做法比「去掉脸」更强：它把脸放在**另一张图**里并用 inpainting mask **保护起来不重绘**——不是「不提供脸」，是「提供脸并锁定它」。

## 一条限制收益的前提

**所有开源视频模型对参考图都是整图过 VAE、拼 token，没有 face embedding 专用通路。** Wan-Animate 的 Face Blocks 处理的是驱动视频的表情，且论文明确说明该通路被设计成与身份属性解耦。

因此**分离本身不产生收益**，收益来自平台侧的 role routing（Gemini 类型化槽位、Vidu subject 分组、Kling Element）或 prompt 里的显式绑定。在 Seedance 这类只有 `@Image1` 序号的 API 上，必须在 prompt 中声明「这几张是同一个人」，且需实测 identity splitting 发生率。

这也是 schema 里必须有 `platform_bindings` 的原因——各平台的 role 能力与数量上限差异巨大（Vidu 每 subject ≤3 张、Kling Element 2–4 张、Runway 每 reference 仅 1 张）。

## 后果

**正面**：每类资产可独立校验；可按平台 role 槽位精确分发；失败模式可归因到具体资产类型。
**负面**：schema 比单数组复杂；资产生产步骤变多（S4 阶段变重）。
**缓解**：S4 的产出做成带质量闸门的流水线（`13-character-assets.md` §3），未过闸不许入库、未锁定不许进入批量生成。

## 待验证

以下机制推理明确但无直接消融实验，建议用自有素材做小规模 A/B：风格化比例角色在去头体型图下的实际漂移幅度（写实比例已有实践验证）；单图 grid 三视图 vs 三张独立图；LoRA 训练集的景别配比（无任何权威来源，网传数字不可信）。
