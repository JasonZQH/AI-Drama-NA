# ADR-0004 · 从第一天使用 S3 兼容存储

- **状态**：已接受
- **日期**：2026-08-10
- **相关**：`10-media-storage.md`

## 背景

系统产生大量媒体文件（单集约 900 MB，60 集的剧约 55 GB）。本地开发阶段最简单的做法是直接写本地文件系统。

## 决策

**本地用 MinIO 提供 S3 API，代码中只使用 S3 SDK，不出现任何本地文件路径操作。**

访问统一走预签名 URL：浏览器播放签 GET，worker 上传签 PUT，provider 拉参考图签 GET。控制面不代理任何媒体字节流。

## 理由

本地文件系统与对象存储的差异不只是 API——预签名 URL、分片上传、内容寻址、生命周期策略这些概念在本地 fs 上没有对应物。如果先用 fs 再迁移，等于重写整个媒体层。MinIO 在 docker 里跑一行命令的事，没有理由不从一开始就用。

**预签名 PUT 直写是关键收益**：远程 GPU worker 生成完直接上传到存储，不需要任何 S3 凭证，也不需要把几百 MB 的视频先传回 Mac 再上传。Mac 的上行带宽不会成为流水线瓶颈。

内容寻址（sha256 去重）在对象存储上是自然的，在 fs 上要自己造。

## 备选与否决理由

| 方案 | 否决原因 |
|---|---|
| 本地文件系统 | 迁移成本高；无预签名；worker 直写不可行 |
| 直接用云 S3 | 开发期产生流量费；离线不可用；上传延迟拖慢迭代 |
| 数据库存 BLOB | 数据库不是文件系统，备份与性能都会崩 |

## 后果

**正面**：本地与云代码零差异；worker 直写；天然去重与生命周期管理。
**负面**：多一个 docker 服务；预签名 URL 有过期语义，前端需要处理 403 重取。
**缓解**：前端 API 客户端统一处理媒体 URL 过期重取；TTL 设为 15 分钟平衡安全与体验。

## 注意事项

远程 GPU 场景下必须区分 `S3_INTERNAL_ENDPOINT`（控制面自用）与 `S3_PUBLIC_ENDPOINT`（签发给 worker）。签出 `localhost` 给远程机器是最常见的集成失败，已在 `11-dev-setup.md` §7.3 单独标注。
