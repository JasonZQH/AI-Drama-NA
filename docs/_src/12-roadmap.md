# 12 · 里程碑与验收标准

> Status: Draft v1 · 2026-08-10

## 原则

每个里程碑都是**可演示的完整链路**，不是「完成了某个模块」。M0 就能从剧本走到播放，后面的里程碑只是把链路里的某一段从假换成真。这样任何时候中断，手上都有一个能跑的东西。

```
M0 骨架          假生成 · 真流程        无 GPU / 无 key
M1 真实生成      云 API · 真成本        一个 provider
M2 自部署        远程 GPU worker        Worker Contract
M3 成片          音频 + 拼接            clean 母版 + M&E
M4 素材产线      分级 conform + 切条     ★ 曝光优先，提前到闭环之前
M5 闭环          播放器 + 分集           端到端
M6 优化          自动评测 + 智能路由     数据驱动
```

**M4 为什么排在 M5 之前**：北美的成本结构是营销约为制作的 9 倍，素材才是投出去的东西。**先有能投的素材，才谈得上验证市场；播放器可以晚一点。** 这是「先打曝光、再优化细节」在里程碑上的落地——把能产生外部反馈的能力尽早交付，把内部体验的打磨往后放。

## M0 · 骨架跑通 ✅ 已完成

**目标**：无 GPU、无 API key，在 Mac 上从剧本走到可播放成片。

**实测结果**：12 镜生成（14 次尝试 / 2 次自动重试）→ 全部选片 → 渲染出
36.02 秒 1080×1920 母版 → 播放页放母版。重渲染复用 12 条规范化产物，4s → 0s。

| # | 交付 |
|---|---|
| 1 | monorepo 骨架，`pnpm dev` 一键起 web + control + worker |
| 2 | docker-compose：postgres / redis / minio / media-worker |
| 3 | 完整 schema + 迁移 + seed（1 集 / 12 镜 / 2 角色） |
| 4 | `packages/contracts` 与 `contracts:build` 链路打通 |
| 5 | `MockProvider`，含 15% 失败率与确定性 seed 模式 |
| 6 | 镜头状态机 + BullMQ 六队列（`q:tts` 留到 M3）+ SSE 进度 |
| 7 | 分镜页、选片页两个核心界面可用 |
| 8 | FFmpeg 规范化 + 拼接，产出可播 MP4 |

**验收**（2026-08-16 在 `51460bc` 上从 GitHub 全新 clone 实测，逐条记录方法与保留）

- [x] **全新 clone 后 5 分钟内跑起来，无需任何外部凭证**
      各步骤实测：clone 1s → `pnpm install` 10s（独立 store，真下载）→ 三个容器 5s →
      `minio-init` 3s → media-worker 9s → `pnpm build` 9s → migrate+seed 2s，合计约 **39s**。
      全程只 `cp .env.example .env`，无任何凭证。
      **两点保留**：① media-worker 那 9s 是 Docker 层缓存命中的结果（只删了 tag 未清 build
      cache），真正的冷构建要装 ffmpeg 与 uv sync，会显著更久；② 本机 5432 被占，
      走了 README §「Port 5432 already taken?」的端口覆盖——该文档解法实测有效。
- [x] **「生成整集」→ 12 镜全部完成，含至少 1 次自动重试**
      dryRun 先报 12 镜 / $0.85 / 未超预算，确认后入队；65s 内 12 镜全部到 `review`。
      Ledger：**14 次尝试 / 12 次采纳 / 2 次失败**——镜头 6 `provider_error`、镜头 11
      `timeout`，均在第 2 次尝试成功。重试是 MockProvider 默认 15% 失败率触发的，
      不是注入的，所以每次跑的具体镜号会变。
- [x] **选片 → 渲染 → 播放器能看完整一集**
      12/12 选片后全部 `locked`；渲染出 36.02s 母版。**真解码验证**（非只看文件存在）：
      `ffmpeg -v error -i master.mp4 -f null -` 退出码 0、stderr 为空；
      ffprobe 报 1080×1920 · h264+aac · 24fps · 36.020996s。
- [x] **杀掉控制面进程再重启，在途任务能恢复（reconcile 生效）**
      4 个 job 处于 `running` 时对 control 与 worker 同时 `kill -9`，并 `redis-cli flushall`
      清空全部队列状态——只留 Postgres。重启后 `reconcile: {requeued: 0, resumed: 4}`，
      4 镜全部跑完。
      **必须说明的机制细节**：恢复后的轮询实际都返回了 `provider_error`，因为
      MockProvider 的任务表是进程内 Map，重启后不认识旧 handle。该错误被正确判为可重试，
      状态机开出 attempt 2 并成功。所以这条验证的是**控制面能从 Postgres 重建在途任务**，
      而「provider 侧继续原来那次生成」要等 M1 接入有服务端任务状态的真 provider 才能验。
- [x] **状态机单测覆盖全部合法迁移与非法迁移**
      88 个用例。矩阵由 `ShotStatus.options × ALL_EVENTS` 动态生成并断言为 7×10=70 组，
      合法组合对照真值表断言 `next`，非法组合断言 `ok === false`。
      另有反向校验：把实际可通过的组合收集成集合与真值表键比对，防止真值表自己写漏。

全新 clone 上跑过完整门禁：单测 / 集成测试 / lint / typecheck 全部通过。集成测试能连上库，
靠的是 `vitest.config.ts` 读 `.env`（本次 Postgres 在 5433，硬编码兜底是 5432）。

> 这里不再写具体的用例数——它在三个 PR 内过期了三次，而任何一次 CI 运行都是更准的答案。

## 关键指标

贯穿所有里程碑，每个阶段都要能回答：

| 指标 | 定义 | 目标 |
|---|---|---|
| **一次通过率** | 首次尝试即被采用的镜头占比 | M1 建立基线 → M6 ≥ 55% |
| **每可用镜头成本** | 总花费 ÷ 被采用镜头数 | 比「每秒单价」有意义得多 |
| **单集墙钟时间** | 从批量生成到成片 | M3 ≤ 2 小时 |
| **人工干预次数** | 每集需要人动手的次数 | M6 ≤ 15 次（主要是选片） |
| **素材赢家率** | 上线渲染中成为投放赢家的比例 | 行业基准约 5%；赢家渲染集中在少数概念上，一部剧收敛到 2–3 个赢家角度（40–60 概念的推导见 `02-data-model.md` §8.5）|
| **单部剧交付物数** | 正片 + 素材 + 商店 + 联盟包 | 600–1200 个 |

`每可用镜头成本` 是最重要的一个——它把重试率、失败率、模型单价合成了一个数字。所有优化最终都体现在它身上。

## 明确不做（本阶段）

| 不做 | 原因 |
|---|---|
| 支付、订阅、权益 | 目标是生产链路；但 Web 结账在架构上须预留（TV-MA 完整版的唯一合法通道） |
| 多用户、协作、权限 | 单人本地 |
| CDN、大规模分发 | 本地文件服务足够 |
| 内容审核闸门 | 字段与钩子留好，逻辑后置 |
| 移动 App | Web 响应式够用 |
| Kubernetes | 单机 + 一台远程 GPU，上 K8s 是负担 |

留位置不等于现在实现——`02-data-model.md` §10 列了所有预留字段。
